# Design — icons-from-ncvue

## Decision 1: Build-time materialization, not runtime consumption

The nc-vue packs are ESM modules of `{ key, label, url }` entries where `url` is a
`data:image/svg+xml,…` URI (generated by `nextcloud-vue/scripts/generate-nl-icons.mjs`, encoded
with the mini-svg-data-uri algorithm). nldesign's public contract is the **PHP-side**
`IURLGenerator::imagePath('nldesign', 'icons/…')` — plain SVG files served from the app
directory, no JS, no controller.

Bridging options considered:

1. **Materialize SVG files at build time (CHOSEN).** `scripts/build-icons.js` imports the three
   pack modules from `@conduction/nextcloud-vue` (npm devDependency), reverses the data-URI
   encoding (`decodeURIComponent` after stripping the `data:image/svg+xml,` prefix — the
   generator's encoding is a plain `encodeURIComponent` with a few safe pairs decoded back, so
   `decodeURIComponent` is an exact inverse), and writes each entry to
   `img/icons/<set>/<key>.svg`. Pros: zero runtime coupling, identical serving path and caching
   behaviour to today, works for PHP/`<img>`/CSS consumers alike, release artefact is
   self-contained. Cons: generated files are committed (as today — `img/icons/` has always been
   build output that ships in the app package).
2. Runtime PHP endpoint decoding the packs — rejected: adds a controller + route + auth surface
   for static assets, breaks the existing `imagePath` contract, and would need the JS packs
   parsed from PHP.
3. Tell consumers to import the packs from nc-vue directly — right for Vue apps (and stays the
   recommendation for them, via `CnIconBrowser` `url-icons`), but does nothing for PHP/template
   consumers, which is the API `img/ICONS.md` documents.

`@conduction/nextcloud-vue` is a **devDependency**: it is consumed only by the build script.
Nothing under `js/` or `lib/` imports it (nldesign remains a no-Vue app).

## Decision 2: Set-prefixed layout `icons/<set>/<key>.svg`

The packs use kebab-case slug keys; the three sets overlap in common names (home, search,
calendar…). A flat directory would need cross-set collision renames that break whenever any
upstream set adds an icon. Instead the filesystem mirrors pack identity:

- `img/icons/rvo/<key>.svg` (1163)
- `img/icons/open-gemeenten/<key>.svg` (256)
- `img/icons/den-haag/<key>.svg` (69)

`imagePath('nldesign', 'icons/rvo/home.svg')` works unchanged (imagePath is a plain app-dir path
resolver). Set prefixes also make licence provenance auditable per file, and keep parity with the
nc-vue module names so a Vue consumer and a PHP consumer can talk about the same icon.

Exact per-set counts are whatever the installed `@conduction/nextcloud-vue` version ships — the
inventory test derives expected counts from the packs, not from hardcoded numbers (the 1163/256/69
split is the count at authoring time).

## Decision 3: Deprecation path — alias files with replacement artwork, one release

The Amsterdam **artwork** must go now (proprietary; we have no licence to ship it at all), so a
classic "deprecated but still shipped" release is not available. What CAN be preserved for one
release is the **URL contract** for stored references (launchpad tile data persists
`/apps/nldesign/img/icons/{Name}.svg` URLs in the DB):

- `scripts/icon-aliases.json`: curated map `{ "Search": "rvo/zoek", "Star": "rvo/ster", … }` from
  legacy PascalCase names to the visually closest pack icon. Curated by hand, best-effort; not
  every one of the 344 names has a sensible equivalent.
- The build writes, for each alias, a **copy of the replacement pack SVG** at the legacy
  top-level path `img/icons/{Name}.svg`. Old URLs resolve to EUPL-compatible artwork that means
  the same thing; no Amsterdam bytes ship.
- Unmapped legacy names 404 immediately; the changelog lists every removed name with its alias or
  "no equivalent".
- Lifecycle: aliases ship in this release only and are deleted in the next minor release
  (`icon-aliases.json` emptied, build stops emitting top-level files). `img/ICONS.md` and
  `CHANGELOG.md` both carry the deadline so the removal is a documented, expected break.

## Decision 4: Logos are static huisstijl assets, out of the build

`img/logos/` (23 files) stays as-is: these are organisation marks displayed as that
organisation's own huisstijl on that organisation's instance, referenced from `token-sets.json`
(`theming.logo`) — nominative use tied to token sets, not icon-library redistribution
(USER DIRECTIVE: logos stay). Consequences:

- `scripts/build-icons.js` no longer copies `node_modules/@amsterdam/design-system-assets/logo/`
  (today's script does — that pipeline dies with the dependency). The checked-in files are the
  source of truth; adding/renaming a logo is a reviewed commit, still governed by the
  naming-stability requirement.
- The `imagePath('nldesign', 'logos/{name}.svg')` contract is unchanged.

## Decision 5: ICONS.md remains generated

`img/ICONS.md` is written by `scripts/build-icons.js` today; that stays, so the inventory can
never drift from the build. The regenerated document gains: per-set inventories with licence and
upstream attribution (pointing to nc-vue `src/icons/ATTRIBUTION.md` as the canonical licence
record), the alias table with the removal deadline, the updated usage snippet
(`icons/rvo/zoek.svg` style paths), and the existing availability/fallback and naming-stability
sections.
