Consequences for our selectors:

- **Explicit dark**: `body[data-theme-dark]` (primary) — also emit `body[data-themes*=dark]` for
  parity with core's icon convention.
- **Auto dark**: `@media (prefers-color-scheme: dark)` — but ONLY when no explicit theme is
  chosen, i.e. the body has neither `data-theme-light` nor `data-theme-dark` (nor their
  highcontrast forms). We cannot key on `data-theme-default` because anonymous pages (login,
  public shares) have NO theme attributes at all yet still auto-follow the OS. Hence the
  media-scoped block uses
  `body:not([data-theme-light]):not([data-theme-dark]):not([data-theme-light-highcontrast]):not([data-theme-dark-highcontrast])`.
- **There is no `[data-theme-dark]`-on-`:root` or `html` variant** — attributes live on `<body>`.

## 2. Generated file shape

`css/tokens/dark/<set>.css` (generated; header comment carries generator version + source set
hash so `occ nldesign:generate-dark-variants` can skip up-to-date files):

```css
/* GENERATED by nldesign DarkPaletteService vN from tokens/<set>.css (sha256:...) — do not edit */
@media (prefers-color-scheme: dark) {
  body:not([data-theme-light]):not([data-theme-dark]):not([data-theme-light-highcontrast]):not([data-theme-dark-highcontrast]) {
    --nldesign-color-primary: ...;
    /* ...all derived/overridden dark declarations... */
  }
}
body[data-theme-dark],
body[data-themes*=dark] {
  --nldesign-color-primary: ...;
  /* identical declaration block */
}
```

Declarations are emitted on `body`-level selectors, which out-specify our light `:root`
declarations from `tokens/<set>.css` without `!important` — cascade-correct and consistent with
ADR-CSS-002 (`!important` only for essential structural rules; none needed here).

## 3. Derivation algorithm (DarkPaletteService)

Input: the parsed `:root` declarations of `css/tokens/<set>.css` merged over
`css/systems/nldesign/defaults.css` (so incomplete sets derive from their effective light values,
same resolution the preview service uses). Output: a map of dark declarations for every
*color* token; non-color tokens (sizes, radii, fonts, urls) pass through untouched and are NOT
re-declared (they inherit from the light layer).

Per color token:

1. **Parse** with `ContrastService::parseColor()` (hex 3/6-digit + rgb()/rgba()); unparseable
   values (gradients, `var()` chains) are skipped — the light value stands.
2. **Convert to HSL**, preserve hue `H` exactly.
3. **Invert lightness**: `L' = 1 − L`, then compress toward the NC dark anchors so surfaces land
   near NC's own dark palette (`DarkTheme::getCSSVariables()` uses `#171717` main background /
   `#EBEBEB` main text — verified in `apps/theming/lib/Themes/DarkTheme.php:47-48`):
   `L'' = 0.08 + 0.84 × L'` for background-class tokens, `L'' = clamp(L', 0.62, 0.92)` for
   text-class tokens. Token classes come from the existing `TokenRegistry` categories
   (background/text/border/status/brand).
4. **Desaturate slightly** for large surfaces: `S' = S × 0.9` on background-class tokens only
   (prevents neon-looking brand walls in dark), `S' = S` otherwise. Hue never changes.
5. **Brand primary exception**: `--nldesign-color-primary` (and `-hover`) keep their light
   L when the paired `--nldesign-color-primary-text` still passes 4.5:1 against them — gemeente
   brand colors that already work on dark stay untouched; only failing brands are lightened.
6. **WCAG verification loop**: run `ContrastService::check()` over its defined PAIRS with the
   candidate dark declarations. For every failing pair, binary-search the foreground lightness
   away from the background (max 8 iterations, step halving from 0.25); if still failing, snap fg
   to `#EBEBEB` or `#111111` (whichever passes) and log a warning. The loop MUST terminate with
   every evaluable pair ≥ 4.5:1 — the generated file is contract-clean AA by construction.
7. **`-rgb` companion variants** are regenerated from their base token after derivation.
8. **Hand-authored overrides win**: if `css/tokens/<set>.css` contains a
   `@media (prefers-color-scheme: dark)` block (parsed via `CssParserService`), its declarations
   REPLACE derived values before step 6 — the verification loop still runs over them, but only
   WARNS (never rewrites) on hand-authored failures: author intent is respected, the warning
   lands in the occ output and the shipped-set audit.
9. **`logo_dark`**: when the set's `theming.logo_dark` manifest key is present, emit
   `--nldesign-logo-url: url('../../img/logos/<file>')` into the dark block (path relative to
   `css/tokens/dark/`). This is the delivery mechanism for the dark logo — NC core has no dark
   logo slot (server#47357), so we own it in CSS.

Generation skips: sets with `design_system: "none"` (nothing to darken — stock NC handles its own
dark) and `design_system: "high-contrast"` (the AAA black-on-white set pairs with NC's own
`dark-highcontrast` theme; auto-darkening would fight its purpose — hand-authored dark blocks
remain possible there).

Re `dark-highcontrast` matching `[data-themes*=dark]`: when a user runs dark-highcontrast, our
dark variables apply AND NC's `[data-theme-dark-highcontrast]`-scoped variables apply on top with
their own values for the `--color-*` layer; our Layer-6 remappings deliberately leave
`--color-main-background`/`--background-invert-if-*` alone (REQ-CSS-007), so highcontrast still
wins where it matters. Accepted overlap, documented here.

## 4. Generation-time write strategy

The app directory is writable in every deployment this app already supports (custom token set
upload writes `css/tokens/custom-*.css` today). Still:

- Shipped sets: generated files are produced at BUILD time (occ command run in CI, wired into the
  existing nightly token-sync workflow so upstream token updates regenerate dark variants in the
  same PR) and COMMITTED — install does not depend on writability.
- Repair step (install/upgrade): regenerates only missing/stale files (hash check); when the
  directory is not writable it logs a warning and skips — theming degrades to light-only, never
  errors.
- Custom uploaded sets: `CustomTokenSetService` gains a post-upload hook that generates
  `css/tokens/dark/custom-<id>.css` at upload time (same service, same writability as the upload
  itself).

## 5. Toggle + user-choice guarantees

- `IConfig` app value `dark_variants` (default `'1'`). `injectThemeCSS()` checks it before
  adding `tokens/dark/<set>`; the admin panel exposes a checkbox; `POST /settings/dark-variants`
  (admin-only, `@AuthorizedAdminSetting`) persists it.
- The app never reads or writes `enforce_theme`, never calls `ThemesService::setEnabledThemes`,
  and emits no CSS that styles dark onto a body carrying `data-theme-light`. A user's explicit
  light choice on a dark OS renders fully light; explicit dark on a light OS renders fully dark;
  auto follows the OS. These three are the live-verification matrix in tasks §6.
